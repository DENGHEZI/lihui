## 一、API 调用策略

### 1.1 为什么必须「批量」

朴素做法：36 个方向 × 每方向 15 次单点算路 ≈ 540 次请求，免费配额（个人认证 5,000 次/日）撑不起几个用户。
鲤慧的做法：**每轮把 36 个方向打包成一次「1×36 批量矩阵算路」**，3 轮二分 + 1 次盲区复核 = **一次体检仅 4 次算路请求**，配额消耗压缩约 **135 倍**。

| 层级 | 接口 | 单次体检调用量 | 说明 |
|---|---|---|---|
| 主链路 | `GET /routematrix/v2/walking` | 3（二分）+ ≤1（盲区复核） | 1 origin × 36 destinations |
| 降级 Ⅱ | `GET /directionlite/v1/walking` | ≤36（并发 8，令牌桶限流） | 仅矩阵不可用时 |
| 设施层 | `GET /place/v2/search` | 6（RRF 复合词，逐关键词二次确认） | 与体检报告共用 |

### 1.2 端点与坐标系参数（2026-10 实测）

百度各产品线参数命名**不统一**且近期改版，以下为真实 AK 实测结论：

| 接口 | 坐标系参数 | 合法取值 | 踩坑记录 |
|---|---|---|---|
| `routematrix/v2/walking` | `coordtype`（无下划线） | `3` / `gcj02` / `gcj02ll` 均收 | 写成 `coord_type` 报 `status=2 coord_type is invalid` |
| `directionlite/v1/walking` | `coordtype`（无下划线） | **仅字符串** `gcj02` | 旧写法 `coord_type=3` 已全线报 `[coord_type] format is invalid`（百度改版，存量代码被本次开发实测暴露并修复） |
| `place/v2/search` | `coord_type`（带下划线） | `3`（数字） | 已加自适应防御：若报参数无效自动换 `coordtype=gcj02` 重试 |

**不传坐标系参数的后果**：入参被按 BD-09 解释，GCJ-02 坐标整体偏移 500~900m——等时圈圆心会「漂」到另一条街。鲤慧全程显式声明 `coordtype=gcj02`，返回不设 `ret_coordtype`（保持 GCJ-02 与端上 `wx.getLocation` 一致）。

### 1.3 返回结构差异（实测）

矩阵接口的 `result[i].distance/duration` 是 **`{text, value}` 对象**而非数字：

```json
{"status":0,"num":3,"result":[
  {"distance":{"text":"1.7公里","value":1715},"duration":{"text":"24分钟","value":1469}, ...}
]}
```

解析层做双形态兼容（`parseMatrixVal`）：对象取 `.value`，数字直接用——防止百度未来回退结构导致静默 NaN。

### 1.4 双配额池隔离（重要实测发现）

**批量算路与 place 检索的配额池互不共享**：当日 place 检索已 302（天配额超限）时，矩阵算路依然 `status=0` 正常返回。

因此熔断也拆成两个独立短路器：

- `quotaBlockedUntil`（place 池）：302/401 → 熔断 10 分钟，只锁设施检索，覆盖率降级；
- `matrixBlockedUntil`（算路池）：302/401 → 熔断 10 分钟，只锁算路。

收益：**检索配额烧完的日子，等时圈（40% 权重的核心功能）照样真算**，不会连坐。

### 1.5 并发容错与限流

- **矩阵整轮失败** → 中止二分，进入降级链（见 2.4）。
- **矩阵部分方向失败**（`result[i].duration≤0`）→ 该方向区间不动，下一轮继续；单轮有效率 <50% 打 warn。
- **并发单点算路**：8 并发 + 令牌桶（130ms/令牌）防止瞬时 QPS 超限；单点失败留空不炸批；遇 302/401 让 worker 提前收工避免空烧。
- 令牌桶实现注意：**只有真正累积令牌才推进时间戳**，否则 `elapsed` 恒为 0、令牌永不回流、并发任务全部挂死（实测踩过）。

## 二、等时圈算法设计

### 2.1 总体思路（官方提示口径）

> 官方：「扇形采样 + 空间插值仅连通区域，无需底层路网数据。」

以家为圆心做 **36 方向扇形采样**，每个方向独立二分「最大可达步行距离」，最后把 36 个离散可达点用 **Catmull-Rom 闭合样条**插值成平滑多边形。全程只依赖批量算路，不需要任何路网底图数据。

### 2.2 参数（官方口径）

| 参数 | 值 | 来源 |
|---|---|---|
| 步速 | 80 m/min | 命题解读官方给定 |
| 路网弯曲系数 | 1.3 | 命题解读官方给定（实际步行距离 ≈ 直线 × 1.3）|
| 方向数 | 36（10° 间隔） | 精度/成本平衡点 |
| 二分轮数 | 3 | 距离分辨率 ≈ 上限/8（≈290m），配合线性外推足够 |
| 二分上限 | minutes × 80 × 1.3 × 1.5 | 弯曲系数基础上再留 50% 富余 |

### 2.3 二分收敛 + 线性外推

每轮：对每方向取区间中点 `mid`，36 个中点打包一次矩阵请求；`duration ≤ minutes×60` 则 `lo=mid`（可达），否则 `hi=mid`（不可达）。

3 轮后，用**最近一次实测点**做速度均匀假设的线性外推：

```
est = probe.dist × (minutes×60 / probe.duration)
radius = clamp(est, lo, max(hi, probe.dist) × 1.05)
```

与二分区间交叉约束，防单点噪声把半径炸飞或压扁；从未测到的方向用全方向中位数兜底。

### 2.4 降级链（三级，逐级显式标注）

```
批量矩阵二分（engine=routematrix-batch，首选）
  ↓ 矩阵整体不可用
并发 directionlite/walking ×36（engine=directionlite-concurrent，令牌桶限流，
  实测耗时反推可达距离 est = idealR × budget/duration）
  ↓ 算路池熔断/全部失败
理想圆（engine=ideal-circle-degraded，半径 = minutes×80×1.3，degraded=true + hint）
```

`engine` 字段随响应下发，前端徽章显式展示——**降级不冒充真算路**，评分口径可审计。

### 2.5 Catmull-Rom 闭合样条

36 个可达点按环形闭合处理（首尾邻居 wrap），每段插 8 个中间点 → 288 点平滑多边形。相比直线连接，消除了「齿轮状」锯齿，贴合真实等时线的凹凸形态（临河/铁路方向会自然凹进去）。

## 三、多源 POI 清洗策略

设施检索复用体检报告的六类口径（`services/lifeShared.js`），清洗管线：

1. **多路召回**：每类 `keywords.join('|')` 复合检索（place 不认 `|`，服务端拆词并行 + **RRF k=60 倒排融合**，多路同时召回且排名靠前的 POI 得分最高）；
2. **二次确认**：复合词空结果时逐关键词补检，取第一个命中路；
3. **坐标清洗**：丢弃 `lng/lat` 非有限数的 POI（NaN 会在距离计算里静默把整格判成盲区——「接口 200 但数据错层」是静默失效的典型来源，必须显式过滤）；
4. **去重**：`uid || name@address` 作键；
5. **失败隔离**：检索异常的类标记 `failed`，**不参与计分**（区别于「确实没有」），权重归一化——偶发网络错误不会把覆盖率拉穿；
6. **类间错峰**：6 类检索间隔 150ms，防百度 QPS 瞬时超限。

## 四、盲区识别算法

### 4.1 口径定义（可解释、可复现）

**论域**：等时圈多边形内部的 N×N 网格（默认 5×5，可调 3~9）。圈外格不算盲——步行本来就超时，与设施覆盖无关（即「空间插值仅连通区域」）。

**格 → 设施步行时间**：`haversine(格中心, 该类最近设施) × 1.3 ÷ 80`（分钟）。官方允许用直线 × 弯曲系数估算设施覆盖，无需逐格真算路（25 格 × 6 类 × 20 设施真算路会烧穿配额）。

**类覆盖度**：`cov_c = max(0, 1 − walk_c / minutes)`；该类无设施 = 0。

**格加权覆盖分**：

```
score = Σ( cov_c × weight_c ) / Σ weight_c × 100
```

权重即六类权重（医疗 .25 / 交通 .2 / 商业 .2 / 教育 .15 / 餐饮 .1 / 休闲 .1）；检索异常类剔除后权重归一化。

**盲区判定**：`insideCircle && score < 40`。

### 4.2 盲区二次矩阵复核（API 深度加分项）

插值多边形是 36 方向的凸包近似，夹角之间的格中心实际可能 >15 分钟（海湾形凹陷）。对全部候选盲区格发起一次 **1×M 批量矩阵实测「家 → 格中心」**：

- 实测 `duration > minutes×60×1.15` → 该格其实是圈外（插值偏乐观），改判 `outsideVerified`，从盲区与覆盖分母中剔除；
- 矩阵不可用 → 跳过复核，沿用插值结论（不阻塞）。

一次体检净增 ≤1 次矩阵请求，换来盲区结论的实测背书。

### 4.3 输出口径

| 字段 | 含义 |
|---|---|
| `coverageScore` | 六类覆盖率按权重归一（圈内格加权均值），0~100 |
| `coverage[].ratio` | 单类覆盖率（圈内格 `cov` 均值），`failed=true` 时为 `null` |
| `blindZones[]` | 盲区格清单（含 score、最近设施步行分钟） |
| `cells[]` | 全部网格（`insideCircle` / `blind` / `outsideVerified` / `score` / `walkMinByCategory`），供热力渲染 |
| `summary.blindRatio` | 盲区格 ÷ 圈内格 × 100% |

## 五、真实对比测试报告

### 5.1 测试环境

- 位置：湖南省郴州市北湖区（GCJ-02 113.014, 25.570，城市中心商圈边缘）
- 时间：2026-10-03（place 检索 302 天配额超限的真实生产环境）
- AK：个人认证免费配额

### 5.2 直线圆 vs 真实等时圈（同一点位，15 分钟）

| 指标 | 直线圆（旧版） | 真实等时圈（本引擎） |
|---|---|---|
| 假设 | 半径 1200m 正圆 | 路网 + 实测 duration |
| 面积 | 4.52 km² | **1.83 km²（−59%）** |
| 各方向半径 | 恒 1200m | **585 ~ 1150m，逐方向不同** |
| 引擎 | — | `routematrix-batch`，3/3 轮收敛 |
| 耗时 | 0 | 1.32s（含 3 轮矩阵 + 盲区复核 13 格 + 6 类检索） |

**结论**：直线圆高估了 59% 的可达面积。按真实路网，80m/min 步速在城市中心因过街等待/支路绕行，有效直线半径仅约 585~1150m——**这正是命题把「等时圈生成」设为 40% 权重的原因**：直线圆会系统性高估生活圈质量。

### 5.3 降级链实测

| 场景 | 触发方式 | 结果 |
|---|---|---|
| place 302 + 矩阵可用 | 当日真实配额状态 | `engine=routematrix-batch`，覆盖率部分降级（`quotaExhausted=true`），等时圈不受影响（双池隔离生效） |
| place 302 + 引擎内矩阵未试 | 首版熔断连坐 bug | 引擎降级 `ideal-circle-degraded`（已修复：算路池独立短路器） |
| 矩阵参数错误 | 旧 `coord_type` 参数 | 3 端点候选自动轮换，全部失败走并发/理想圆（日志可追溯） |

### 5.4 复现方式

```bash
# 服务端
cd 03-lh-server && node src/app.js
# 等时圈（lng/lat 换成任意 GCJ-02 坐标）
curl "http://127.0.0.1:8809/api/v1/life/isochrone?lng=113.014&lat=25.57&minutes=15&grid=5"
# 关键字段：engine / polygon / blindZones / coverage / summary.verifiedCells
```
